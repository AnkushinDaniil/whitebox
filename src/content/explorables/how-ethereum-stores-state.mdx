Ethereum's world state is a map: address → account. Hundreds of millions of
entries, mutated thousands of times per block. Yet a block header commits to all
of it with a single 32-byte field, `stateRoot`. Change one account's balance and
that number must change — and every node on Earth must compute the *same* new
number, independently, with no coordination.

That's the real job: not "store the data" (any database does that) but **commit
to the data** so the commitment is canonical, cheaply updatable, and cheaply
*provable*. The structure Ethereum uses is the Merkle-Patricia Trie. Let's open
it up — and since the whole thing is built out of hashing, let's start the
machine there.

<DepthLayer tier="intuition">

## The machine that folds data into a fingerprint

Every node in the trie is identified by the hash of its contents. So before
anything else, get a physical feel for what a hash *is*: a machine that eats any
amount of data and always spits out the same fixed-size fingerprint — where
changing the input by a hair changes the output completely.

Type into the hopper. Then hit **nudge** and watch the avalanche.

Now picture a filing cabinet where every drawer's label is the fingerprint of its
contents. Change one sheet of paper and that drawer's label changes — which
changes the label on the cabinet holding it — all the way up to one master label
on the front of the building. Read that one master label and you've fingerprinted
the entire archive.

A <KeyTerm term="Merkle tree" def="A tree where each node's identity is the hash of its children. The single root hash commits to every leaf — and you can prove any one leaf with just the hashes along its path." /> gives
you exactly that. But Ethereum's keys are 32-byte hashes, effectively random, so
the structure must *also* be a **trie**: a tree indexed by the digits of the key,
so a lookup is "follow the key, nibble by nibble." Put those together — a trie
addressed by hashing — and you get a lookup index that is *also* a cryptographic
commitment. Everything below is the engineering to make that efficient.

</DepthLayer>

That locality is the payoff. An edit touches only the nodes **on the path from
the leaf to the root**; every other branch keeps its old hash. That's what makes
state updates cheap — and it's exactly what a Merkle proof ships to prove one
account without the whole tree.

Three node types do all the work: a **branch** is a 16-way fork (one slot per
nibble `0–f`); an **extension** is a shortcut that swallows a run of shared
nibbles; a **leaf** is the end of the road, holding the value. Add two keys that
share a long prefix and watch an extension appear; add a third that diverges and
watch it split into a branch.

</DepthLayer>

## Grounded in the spec

Two encodings make the trie deterministic across every client. **RLP** (Recursive
Length Prefix) serializes each node before it's hashed; **hex-prefix encoding**
packs a node's nibble path plus a flag — leaf vs. extension, odd vs. even length —
into bytes.

<SpecExcerpt
  source="Ethereum Yellow Paper"
  href="https://ethereum.github.io/yellowpaper/paper.pdf"
  ref="Appendix D, Modified Merkle-Patricia Tree"
>
The trie's node-cap function hashes a node's RLP only when it is at least 32
bytes; shorter nodes are **inlined** directly into their parent. That one rule —
embed if `len(rlp) < 32`, else reference by `keccak256(rlp)` — is the single most
common reason a hand-rolled trie's root fails to match a client's. (Insert a tiny
value in the widget and watch a node flip to `· inline`.)
</SpecExcerpt>

The empty trie is the hash of an empty string's RLP — a constant every client
hardcodes:

```text
keccak256( rlp("") ) = keccak256(0x80)
= 0x56e81f171bcc55a6ff8345e692c0f86e5b48e01b996cadc001622fb5e363b421
```

## What's actually in a leaf

For the **state** trie, the key is `keccak256(address)` and the value is the RLP
of the account's four fields:

<SpecExcerpt
  kind="code"
  source="execution-specs"
  href="https://github.com/ethereum/execution-specs"
  ref="state account"
>
```python
class Account:
    nonce: Uint           # transactions sent from this account
    balance: U256         # wei
    storage_root: Root    # root of THIS account's storage trie (tries nest!)
    code_hash: Hash32     # keccak256 of contract code (empty-code hash for EOAs)
```
</SpecExcerpt>

Note `storage_root`: each contract account holds *another* MPT for its storage,
and that sub-trie's root is a field inside the account leaf. A write to one
storage slot propagates a new storage root into the account leaf, which
propagates a new state root into the header — the same ripple you just scrolled
through, nested one level deeper.

<Callout type="note" title="Secure trie">
Real keys are `keccak256(address)`, not the raw address. Flip **Secure trie** in
the visualizer: the structure flattens out, because hashed keys are uniformly
distributed and almost never share prefixes. Great for balance — and terrible for
witnesses, which is the whole next section.
</Callout>

</DepthLayer>

## The witness problem (and the road past the MPT)

Here's the bill the hexary MPT runs up. To **prove** one account without holding
the whole state — what a <KeyTerm term="stateless client" def="A node that verifies blocks using witnesses (proofs) supplied with the block, instead of storing the full state itself." /> needs
— you must reveal, at every level, the *sibling* hashes the prover didn't take. A
16-way branch means up to 15 siblings per level. Multiply by depth and witnesses
balloon into megabytes per block. That's the roadblock to statelessness.

The fix is to change the commitment scheme, which changes the optimal tree shape.
Switch between the three designs:

<WidgetFrame
  title="Hexary MPT → Verkle → Binary"
  caption="The same account, proven three ways. Watch how node arity and witness size trade off — and why the roadmap moved."
>
  <StructureCompare client:visible />
</WidgetFrame>

For years the answer was **Verkle trees**: replace Merkle hashing with vector
commitments, so a node commits to all 256 children in one short proof and
siblings stop mattering. Witnesses collapse from megabytes to tens of kilobytes.

Then, through 2024–2025, the roadmap pivoted. The leading direction is now a
**binary Merkle tree** (EIP-7864): arity 2, one sibling per level, ordinary
hashing — no novel cryptography, no trusted setup, and crucially it's friendly to
the <KeyTerm term="SNARK provers" def="Systems that produce succinct proofs that a computation (here, block validation) was done correctly. Simple hash-based trees are far cheaper to prove inside a SNARK than vector-commitment schemes." /> that
will eventually verify Ethereum's state transitions. Binary trees give up some of
Verkle's witness compression for radical simplicity and provability.

<Callout type="warning" title="Moving target">
This is live protocol design, not settled history. Verkle was the plan; binary
trees (EIP-7864) are the current front-runner; specifics are still moving. The
durable lesson is the relationship: **commitment scheme → tree shape → witness
size.** Hold that, whatever wins.
</Callout>
